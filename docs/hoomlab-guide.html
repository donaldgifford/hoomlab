hoomlab

An opinionated, self-hosted, cloud-like platform for homelabs, built on Proxmox VE and Talos Kubernetes. "The opinions are the product." The aim is to be simple (few concepts, one way to do each thing, every decision written down), not easy: the operator is expected to understand what they run.

Today the repo ships the bootstrap CLI (tools/bootstrap). It takes bare Proxmox nodes to a healthy Talos cluster from one HCL file. The hoomlab service and its Helm chart are scaffolded around it: a release train, a chart contract and a stub binary.

What hoomlab is

RFC-0001 names two problems. First, home IaC is invoked, not resident: nothing reconciles between runs, and a state file becomes a third truth beside the config and the world. Second, production-like systems at home are a big investment of bespoke assembly. hoomlab answers with two deliverables, built strictly in order.

Bootstrap CLI built

An out-of-cluster, operator-run CLI in tools/bootstrap (its own Go module). Each stage is a command that checks the world, applies only the delta, and is safe to re-run. There are no state files.

hoomlab service stub

cmd/hoomlab only prints its version. The plan is a resident reconciler, deployed by the chart, that reads the same HCL and so "owns itself".

Helm chart built

charts/hoomlab: the deployment contract (env vars, probes, envFrom, collision guard). It has 8 helm-unittest suites with 45 cases and a JSON schema.

Release train built

Merging to main with a semver label tags a version. Binary, image and chart publish in lockstep, signed with cosign and carrying SLSA provenance. Tools release on demand under their own tags.

One rule ties it together: the config file and the world are the only two truths. Every step reads actual state and converges toward the config, so an interrupted run is re-run, not repaired. Disaster recovery is the same act as the first bootstrap.

Completion tiers and the ownership boundary

DESIGN-0002 defines "done" for bootstrap as T2. Anything past it belongs to the GitOps/IaC layer. The rule: if it must be decided at image-build or machine-config time, bootstrap owns it; if it is expressible as a Kubernetes API object on a running cluster, the IaC layer owns it. Part 2 · Bootstrap CLIStage chain: bare metal to a running cluster

Every stage is its own cobra subcommand. There is deliberately no bootstrap run meta-command (DESIGN-0001 OQ-7). Each stage runs validate first and prints a next: hint. Click through the chain.

The Step / Runner engine

internal/steps is the whole convergence engine: a stage is an ordered list of Step{Name, Check, Apply}. Check never writes, and Apply returns only once the change is effective. Dry-run calls only Check. Try it on a simulated pve form: break a run halfway, then re-run it.

type Step struct {
    Name  string
    Check func(ctx context.Context) (done bool, err error)
    Apply func(ctx context.Context) error
}
type Runner struct { DryRun bool; Out io.Writer; Log *slog.Logger }

  

  
Why no plan or state file: a persisted plan is a third truth that can go stale (INV-0003 rejected one from a sibling project). Here the re-run is the resume, because finished steps now check as done.






  
The HCL surface

  
One bootstrap.hcl holds everything the service will also need. CLI-only concerns are flags (DESIGN-0001 OQ-8). Secrets are never values: they're env("HOOMLAB_…") references, resolved at load, so the same file works for the CLI (exported variables) and for the future service (a Secret via envFrom). Resolver and the XOR rule

  
The config pipeline is parse → decode → resolve → validate → render. DESIGN-0004's principle is primitives first: inline attributes are ground truth, and named planes are the first abstraction on top. A network_interface either references a plane or states its facts inline. Both or neither is an error, never an override, and there is no implicit default network.

  

  

    
  

  






  
Profiles → schematics → template classes

  
Extensions are grouped into named profiles, and nodes list profiles. Each unique flattened extension set becomes one content-addressed Image Factory schematic. Emit keys templates and booty profiles by (role, schematic), and after DESIGN-0005 Phase 3 also by label set. A role only splits when something actually differs. Part 3 · The Talos clusterThe VM boot contract

  
talos vms pins every PVE setting that is load-bearing. Drop any one and you get a VM that "looks fine, never boots". The drill found two of them the hard way (INV-0001 deviations 12 and 14). Untick one to see the failure.

  

    

    

  






  
Network planes

  
IMPL-0003 gave every node a second NIC on a storage plane. The primary plane carries PXE, DHCP and node traffic at MTU 1500. The storage plane is static, MTU 9000, and unroutable by construction: no gateway, routes or DNS, so its unroutability is the access boundary. Click a plane.

Part 4 · This branchDESIGN-0005 / IMPL-0004

  
DESIGN-0005 (Talos 1.13.11 upgrade with Kata isolation and cluster options) was Approved at the Phase 2 gate on 2026-10-19, and IMPL-0004 is In Progress. The work runs in two stages: Stage 1 is the upgrade and image work plus a hand-applied Kata test, and Stage 2 builds the CLI surfaces on what Stage 1 proved. Click a phase.

  

  

  
Direction change (2026-10-17, now the design): there is no dedicated, tainted CI pool. Kata is opt-in per workload, CI or not. Placement is a preference carried by a label and the workload's affinity, not a taint. The first user is the Buildkite agent-stack-k8s privileged controller.






  
Stage 1 findings

  
Measured on the live fleet with the T1–T8 test kit (kernel boundary, networking, PVCs, privileged DinD and BuildKit, placement, cold start, reboot recovery). These numbers set the RuntimeClass overhead.

  

  

    

    

  

  






  
Kata per workload

  
runc stays the only default runtime, everywhere. Making a sandbox a node's default would push Cilium, the CSI node plugin and every hostNetwork DaemonSet into a VM they can't run in. Kata is a capability on every worker, opted into per pod. Four layers, each owned once:

  

  
The GitOps contract: one RuntimeClass


apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata: { name: kata }
handler: kata                              # Cloud Hypervisor; the only handler the extension ships
overhead:
  podFixed: { memory: 250Mi, cpu: 250m }   # T7 measured ~200 MB per idle pod (README says 130Mi)
scheduling:
  nodeSelector:
    runtime.hoomlab.io/kata: "true"        # derived by bootstrap from the profile, version-free

  

    
Why a derived label?
Talos labels extensions.talos.dev/kata-containers=3.32.0, and a nodeSelector is an exact match. Selecting on it would leave every Kata pod Pending at the next Kata bump.

    
The Cilium rule
Socket LB can't hook a guest kernel, so socketLB.hostNamespaceOnly: true must be set explicitly whenever any node carries Kata. Bandwidth manager plus Kata is an error (talos#13745).

    
CI pod shape
Run dockerd or buildkitd as a sidecar driven from the command container, because kubectl exec into a cgroup-nesting daemon hits EBUSY. Put /var/lib/docker on a memory emptyDir: virtio-fs can't be an overlayfs upper layer.

  

  
Live migration: a VM can't live-migrate while a Kata guest runs inside it. Kata pods can land on any worker, so turn off automatic live migration for worker VMs (the load balancer's rebalancing, and an HA migrate shutdown policy), and drain before any manual migration. HA cold restart after a host failure is fine.

The day-2 apply stage planned

  
Today the CLI only feeds booty, which a node reads once, at install. Every option in DESIGN-0005 is a machine-config change, so IMPL-0004 Phase 3 adds bootstrap talos apply. It is opt-in, never part of a chain, and scoped by --node. Step through one node.

Release train simulator

  
Releases happen on merge to main, never from a hand-pushed tag. Versions are lockstep: binary, image and chart carry the same tag. Pick the PR's label and what it touches. (The example assumes the last tag was v1.4.2.)

Tools release separately and on demand. tools-release.yml (workflow_dispatch) cuts a tools/<tool>/vX.Y.Z nested-module tag and publishes binary archives only: no image, no chart. A tools-only PR merges with dont-release, so the main train stays inert.
